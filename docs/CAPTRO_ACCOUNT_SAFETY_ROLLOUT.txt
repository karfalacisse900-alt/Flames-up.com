   become server-only, private profile SELECT is revoked, membership reads use
   nonrecursive private helpers, direct client group enrollment is removed.
2. 20261013154326_security_media_approval_boundary.sql: revoke media mutation
   privileges (including explicit column grants), remove owner write policies.
   Preserve owner reads, all media rows and originals. The Worker alone sets
   upload/moderation status, URLs, metadata and crop fields after authorization.
3. 20261013154328_single_owner_push_registration.sql + Worker endpoint: retain
   push rows, deactivate all ambiguous duplicate active bindings until registration,
   enforce one active owner per token hash and transfer ownership atomically in
   a service-only SECURITY INVOKER RPC. Direct client token access is revoked.
4. Native client: reject stale session results/retries, pin old-account push
   unregister requests, serialize account transitions, retain scoped drafts.
5. Worker feature retirement: reject new ordinary posts without media, new poll
   configuration/votes, new voice uploads/assistant sessions/voice attachments.
   Existing records, authorized legacy reads/deletion and moderation jobs remain.

COMPATIBILITY
Current native code uses authenticated Worker endpoints for these writes and
profile projections, not Supabase table writes. Upload uses /media/upload-intent
and /media/complete. Poll/voice request fields are no longer sent by the revised
client. Structured post, RSVP, membership, ticket, reward and payment routes are
not retired. Server access checks remain in those routes.

Older 616.1 clients retain media publishing, comments, messages and notification
endpoint shapes. After retirement deployment, old text-only/poll/voice attempts
receive an explicit 400/410; drafts/data are not deleted. Older direct-Data-API
clients, if any exist outside this repository, must be audited before rollout.
Push registration's RPC requires its migration FIRST. An older Worker can fail
registration on conflicting ownership between migration and Worker deployment;
it fails closed rather than creating two active owners. Plan a short coordinated
rollout, not an unbounded gap. Do not suppress or silently fall back on failures.
Ambiguous devices will temporarily miss notifications until re-registration.
SQL cannot infer the active account on an old token-only client; verify device
re-registration with the corrected app rather than treating this migration as
proof that every old device now belongs to the right account.

ROLLBACK / STOP CONDITIONS
Stop if legitimate Worker writes or user authorization fail in staging. Each
migration is transactional; a failed migration rolls back its own statements.
If production compatibility fails, pause rollout and roll back the Worker only
when compatible with the retained RPC/boundary. Keep the server-only security
boundary. Do NOT restore broad client grants, re-enable client media approval,
or activate multiple push owners as a convenience rollback. Repair the specific
server flow or narrowly reviewed grant. Preserve all posts/votes/media/drafts.
The push RPC and index are additive: retain them when rolling the app back.
