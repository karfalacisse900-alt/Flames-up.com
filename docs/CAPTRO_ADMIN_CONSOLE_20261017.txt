WORKING BEHAVIOR
Reports:
- Existing Report API/database queue reused; no automatic ban based on volume.
- DB-side search, status/assignment/priority filters, ordering and bounded pages.
- URL retains selected case/filters/page. Section list positions are retained.
- Independent summary counts report failures instead of pretending to be zero.
- Selected case uses request identity guards, explicit missing/deleted target state,
  stable preview, retry, creator, reason, internal note and protected history.
- Review, assign, note, duplicate grouping, escalate, dismiss and case resolution
  use confirmed server results. Duplicate grouping requires the same actual target.
- Resolving a report DOES NOT remove content; the interface explicitly says so.

Users and access:
- Server-side canonical ID/username search; email search requires private-read
  permission. User state/version, reports, public posts and history reuse real routes.
- Warn, scoped timed restriction, timed suspension, ban and reinstatement are
  separate commands with reason, target, confirmation and stale-version checks.
- Restrictions include commerce; enforcement checks existing API sessions. Bans
  preserve financial/account records and session-revocation markers on reinstatement.
- Fresh trusted role lookup on requests; owner/moderator/support permission checks.
  Client-provided role/email/localStorage cannot grant authorization.
- Role changes, ban and reinstatement require verified JWT aal2 AND a recent TOTP
  amr timestamp. A freshly refreshed token's iat is NOT a substitute for recent MFA.
- Last-owner check counts active, existing owner accounts, not unusable role rows.
- Open console rechecks access; revoked access clears the interface. Transient
  auth failures preserve the session and offer retry; 403 is not auto-refreshed.

Other sections:
- Content and Stories metadata, media metadata, purchasable listings, operations,
  appeals, role assignments and audit history use bounded server pages.
- Existing financial support view remains permission-restricted/read-only here;
  no generic balance, payout, refund or ticket editing controls were added.
- Appeals can enter independent review and be upheld, linked to the original
  decision. RPC submission enforces ownership and replay uniqueness. User-facing
  notices exclude internal notes. See missing end-to-end work below.
- Metadata lists do not expose provider secrets, storage keys or private URLs.

ACTION / DATABASE CONTRACT
New prepared migration: supabase/migrations/20261017131303_admin_console_workflows.sql
Created using the Supabase migration CLI; NOT applied to production.
Adds report/role versions, service-only operations and appeals, mutation/appeal RPCs.
Each authorized operation is serialized by actor+operation ID, checks the current
record version, writes outcome/audit atomically, and replays the original result.
Different payload with the same operation ID is rejected. Failed mutation attempts
inside the RPC retain a redacted durable outcome/audit. No provider network call is
made while holding these database locks. Ordinary clients have no table/RPC access.
The Supabase skills informed service-only privileges, short transactions and staged
rollout; no client policies were broadened to make the console work.

The browser prevents duplicate submission and, after an ambiguous network result,
queries the actor's durable operation before retrying with the same ID. It does not
optimistically claim success. Native confirmation dialog supplies focus/escape.
Body validation, per-action authorization and existing write rate limit are enforced
on the server. Admin responses are private/no-store. Existing trusted authentication
and origin handling are reused; real deployment CORS/CSP/MFA configuration is unverified.

OPEN REQUIREMENTS / RELEASE BLOCKERS — DO NOT CLAIM COMPLETE
1. Earlier security migrations and actual deployed privileges have NOT been freshly
   certified. Prepared console guard checks only selected grants, not all security
   invariants. Full direct-DB restriction/revocation acceptance remains required.
2. Source-enforced content quarantine/hide/removal/restoration across private media,
   variants/CDN caches, Home, search, Stories and profile is NOT implemented here.
   Media/Stories lists are metadata-only; authorized private/video evidence preview
   and restoration flows need further work. Disabled controls say so.
3. Durable permanent deletion/resource preview/retention and partial cleanup failures
   are NOT implemented/tested by this console patch. Banning is never deletion.
4. Appeals lack the app-facing submission route/form and safe overturn/restoration
   workflow. Review/uphold is only a partial workflow, not complete appeal acceptance.
5. Sensitive role/ban operations require recent MFA, but enrollment/challenge UI and
   approved identity configuration are not part of this patch. Do not remove the
   backend MFA guard to enable a button.
6. Legacy unversioned admin writes are blocked with 409. Until equivalent safe
   content workflows exist, deploying this candidate would pause some existing
   moderation actions. This is a deliberate release blocker, not ready migration.
7. Listing moderation -> affected paid-purchase review linkage is NOT implemented.
   Existing financial records/entitlements are untouched, not automatically revoked.
8. Authentication/validation/rate-limit rejections occurring before the RPC are not
   all durable audit entries; SQL-authorized success/failure outcomes are. Complete
   privacy-safe pre-RPC failure auditing before claiming every attempt is retained.
9. Pending operation UUID is retained during the confirmation dialog, not across
   browser restart. Durable history exists, but cross-relaunch recovery UI is open.
10. No bulk actions shipped. No production full-schema integration, cross-account
    staging tests, direct-media revocation proof or distributed concurrency tests.
11. Final brand asset, manual accessibility/keyboard traversal, Safari, portrait
    tablet and extreme text-size acceptance remain. No native scrolling/device or
    iPhone performance claim is made by any of these admin tests.
