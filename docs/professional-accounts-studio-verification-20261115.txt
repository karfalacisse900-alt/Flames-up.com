IMPLEMENTED
1. iPhone Settings / application
   Apply independently for Creator / Gig and Business. Optional HTTPS links;
   business operating area and pickup preference; explicit public versus reviewer-only
   fields. Save draft, cancel unsaved edits, submit, see review status and applicant
   message, revise and resubmit. Submission never grants a role. Existing accounts
   keep regular features. No banking or identity-document fields were added.
2. Review / role lifecycle
   Existing private admin console has a paginated Professional accounts queue,
   applicant details, reasoned approve/request-changes/decline decisions, private
   internal notes and audit history. Owner/admin only, fresh server authorization.
   Independent suspend/restore/remove actions for each role. Version checks and
   idempotent operation IDs protect against repeated and concurrent decisions.
   Role removal does not delete posts, accounts, purchases or financial journals.
3. Public profile / eligibility
   Explicit public projection includes active approved roles, public descriptions,
   links, authorized portfolio posts and eligible published/unpaused business menus.
   Regular and pending accounts have no creator Support or business Menu from an
   application. Dual-role profiles can switch their professional presentation.
   Existing Follow, Message, Moments, Plans, Clubs and grid behavior are retained.
   A real future hosted plan can supply the compact gig row; no synthetic gig is added.
   Support requires active Creator approval AND existing Stripe/readiness/storefront
   checks. Approval never enables checkout or changes rollout/payment flags.
4. Captro Studio (unpublished)
   Separate responsive website; existing account/password authentication, or a
   single-use 60-second handoff from Settings for existing Apple/Google sessions.
   Handoff becomes a narrow, revocable one-hour Studio credential. Exact-origin and
   method/path restrictions; no admin, publishing, account-security or payment-creation
   endpoints are granted to the delegated token. Account and role checks remain on
   the server for every protected action. No second account or onboarding system.
   Creator: public info, authorized portfolio selection, existing post visibility/pin,
   editable existing gig details, actual Support readiness, ledger and payout history.
   Business: public info, storefront photos through existing approval pipeline, hours,
   dated movable-vendor pickup location/instructions, menu/category/prices/finite stock,
   QUICK_ADD/CUSTOMIZE options, ordering pause, existing orders and one-use pickup
   verification, sales/history. Native camera QR scanning remains available; Studio
   accepts a connected QR reader or pasted pickup code, not a new camera scanner.
   Both roles can switch workspaces. Suspended/removed roles retain history and existing
   order resolution while new ordering and editing are denied. Legacy business owners
   retain native Settings access to existing orders without automatic approval.

PREPARED MIGRATION / CONFIGURATION
The migration depends on the existing app_users/admin_roles/purchases infrastructure
and 20261112030025_captro_business_ordering.sql. Read-only production catalog inspection
found Business and Professional tables absent. Do not apply the new migration alone
against that schema. It was exercised in isolated PGlite Postgres with the existing
Business ordering migration, RPCs and fixture financial lifecycle.
The migration grants no anonymous/authenticated table access. Service-only RPCs use
trusted account IDs, active account status and server-managed admin roles. No role is
backfilled from email, profile metadata, historical payments or application submission.
Finite stock defaults to NULL (unlimited), preserving old records; no old commitment
is reinterpreted. Only cancelled, unpaid awaiting_payment orders release reserved stock.
Fulfillment/refund updates remain possible after role suspension/removal.

Future approved rollout sequence:
- Review Business migration dependencies and current production schema first. Take the
  established backup and rehearse restoration/forward repair in a disposable database.
- Apply the prepared schema before deploying a Worker that reads it. No live Support
  or Business checkout flags are enabled as part of these changes.
- Configure CAPTRO_STUDIO_ORIGIN to the final owned HTTPS root origin (currently unset).
  VITE_CAPTRO_API_BASE defaults to https://api.flames-up.com/api; use the matching test
  API for isolated verification. Align Studio public/_headers connect-src with that API.
- Verify actual email/password login and iPhone Apple/Google handoff, expiry, logout,
  revocation and origin checks against that environment. Browser fixtures alone do not
  verify provider OAuth, live credentials, email delivery or cross-device handoff.
- Deploy matching Worker/admin/native only after separately authorized validation.
  Studio remains unpublished until explicitly authorized. Review existing creators and
  businesses explicitly; no automatic grants are supplied.
- Keep reconciliation and historical order/refund endpoints active during rollout or
  incident gating. Prefer disabling new professional mutations/checkouts and forward
  repair over dropping role/audit/session/financial data. Do not roll back to a Worker
  that omits professional checks while leaving new commerce available.
