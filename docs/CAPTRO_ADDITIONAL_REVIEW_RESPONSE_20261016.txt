1. CURRENCY CORRECTNESS
Initial classification: CONFIRMED source bug, not an observed customer charge.
Root cause: the active creator used all ISO codes but multiplied every price by
100; labels divided by 100; backend accepted arbitrary three-letter currencies.

Changes:
- One resource contract, CaptroCurrencyContract.json, is consumed by native code,
  backend validation and admin finance formatting. Initial explicit set: USD and
  JPY. Unmodeled provider special cases are rejected rather than guessed.
- CaptroMoney parses exact decimal/grouped input into integer units; precision,
  bounds and supported currencies are checked. No floating-point price scaling.
- Currency pickers and paid drafts use that contract. Legacy event price editing
  and validateCreatorEvent now apply the same precision rules, retaining free
  informational event prices and the existing comma-decimal draft compatibility.
- Backend requires a versioned non-USD contract, rejects old ambiguous non-USD
  creation, and gates legacy unversioned non-USD checkout for review.
- Fixed fees are currency-specific. USD retains its configured legacy units;
  JPY requires explicitly reviewed CAPTRO_CURRENCY_FEES. No invented FX rate or
  production configuration was supplied. Purchase totals honor who pays the fee.
- Admin totals/refunds use exact provider-unit formatting. Unknown historical
  currency units are labeled as such, not silently divided by a guessed exponent.
- Ledger/report queries already group by currency; they were not replaced.

Files/functions:
  ios_native/MIRA/Sources/MIRANative/Resources/CaptroCurrencyContract.json
  ios_native/MIRA/Sources/MIRANative/Models/CaptroCommerce.swift (CaptroMoney, draft)
  ios_native/MIRA/Sources/MIRANative/Models/CaptroEventDraft.swift
  ios_native/MIRA/Sources/MIRANative/Screens/{CaptroCommerceEditor,
    CaptroEventEditor,NotificationLibrarySearchCreateViews,CaptroCommerceDetailViews}.swift
  backend-cf/src/{currency,commerce,post-objects}.ts
  backend-cf/src/index.ts (fee config, publication, purchase quote/creation)
  admin-web/src/FinancePage.tsx

Evidence: USD 10.00 -> 1000; JPY 1,000 -> 1000; provider request mocks retain the
same integer total; refund forwarding retains units; invalid precision/codes
fail. Native parser and event-editor tests cover the corresponding inputs.

Status: PARTIALLY FIXED / implementation tested; commercial enablement pending.
JPY fee policy, provider minimums for the actual settlement currency, seller
settlement/payout compatibility and Stripe TEST acceptance remain required.
The existing instant payout flow is USD-only; this patch does not promise JPY
instant payouts. No historical price was rewritten. Inspection plan: enumerate
non-USD price/purchase snapshots in an approved, access-controlled environment;
compare creator intent and provider units; quarantine ambiguous unpaid prices;
ask creator confirmation before replacement/versioning; preserve paid snapshots
and accounting records. Never blanket-divide historical rows by 100.

2. HOSTED CHECKOUT EXPIRY / LATE PAYMENT
Initial classification: CONFIRMED source/SQL lifecycle defect.
Root cause: DB wall-clock expiry released hosted holds without provider state;
Checkout independently expired 35 minutes after creation; late confirmation
rejected the now-expired purchase.

Changes: hosted-hold.ts reconciles fresh provider state, rereads after an expiry
race, retains processing/ambiguous payments, and releases only after terminal
unpaid evidence. The scheduled path and webhook/status recovery cover hosted
payments as well as native. Creation failures no longer release a possibly
accepted provider operation. Checkout uses the canonical stored hold deadline.
The old SQL clock-only release helper becomes a compatibility no-op. Network
calls stay outside DB transactions. Confirmation remains idempotent.
Verified legacy late payments create a service-only app_payment_recovery record
instead of resurrecting sold inventory or auto-refunding. Buyer status says
payment_received_under_review; admin exposes an explicit recovery count.

Files: backend-cf/src/hosted-hold.ts; index.ts (createCommerceCheckoutSession,
completeCommercePurchaseFromSession, reconcileHostedPurchase, scheduled holds,
purchase status); migration 20261016214657; admin dashboard files.

Evidence: mocked paid/delayed webhook, completion racing expire, processing,
cancel timeout and network failure; actual Worker request adapter deadline and
integer amount checks; SQL elapsed hold plus duplicate confirmation yields one
entitlement. Separate PostgreSQL connections ran release/confirmation overlap.

Status: PARTIALLY FIXED. Stripe TEST lifecycle/late-webhook verification and an
approved operator recovery runbook are release gates. No automatic real refund.
An unresolved, missing Checkout ID can conservatively retain inventory when
idempotent provider lookup/replay cannot resolve it. Very delayed creation may
hit Stripe's minimum future Checkout expiry. Old unresolved holds can also
consume the scheduled oldest-40 batch; durable retry scheduling/operational
alerting should be completed before enabling this rollout at scale. The durable
paid-recovery record is not itself proof of completed fulfillment/refund.
The appendix's reverse_transfer hypothesis remains UNCONFIRMED and unchanged.
