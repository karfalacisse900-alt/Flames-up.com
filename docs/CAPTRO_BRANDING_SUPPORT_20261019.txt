2. SUPPORT ARCHITECTURE AND PAYMENT RESPONSIBILITIES

Existing charge model: Stripe platform charges with deferred separate transfers
to existing verified Connect accounts, manual payout/settlement controls.
Support reuses app_purchases, app_payments, app_creator_earnings and the existing
append-only marketplace ledger. No new wallet, connected account, webhook
endpoint, native PaymentSheet path or duplicate payout engine was added.

Amounts are integer USD provider units, $2–$200, with suggestions $2/$5/$10/$20.
Exact parsing rejects fractional cents and out-of-range values. No currency
expansion or historical price reinterpretation. Quantity is one. Support grants
no entitlement, content, badge, visibility, membership or other benefit.

Fee contract:
- Support snapshots and SQL constraints require zero Captro/platform fee,
  zero service-fee line and zero tax line in this development model.
- Checkout does not request application_fee_amount or transfer_data. Existing
  marketplace price/fee calculation is bypassed only for creator_support.
- Existing trusted confirmation reads actual Stripe processing costs and
  accounts for creator net. Test fixture: gross 500, actual fee 59, net 441,
  Captro commission 0, pending earnings 441; this is not a quoted Stripe rate.
- Existing audited release approval, known processing-cost and settlement gates
  remain mandatory. Confirmation does not initiate an automatic transfer.
- With the existing separate-charge model, Stripe initially debits the platform
  for processing costs, refunds and disputes. Modeling creator net does not
  eliminate Captro's provider liability. Unrecoverable fees/negative balances and
  contractual liability need explicit approval before live activation.
- Actual platform pricing configuration and fee payer settings were not verified
  against the Stripe account. Payout fees remain a distinct existing ledger concern.

Backend changes:
- backend-cf/src/creator-support.ts: bounded inputs, exact amount contract,
  scoped HMAC handoffs, authenticated eligibility/receipt routes, strict owned
  browser origin, rate limits and sanitized errors. Bearer handoff expires in
  2 hours; only its hash persists server-side. It is not an app login token.
- backend-cf/src/index.ts: narrow service adapter and support branch in the
  existing createCommerceCheckoutSession. Fresh canonical account, restrictions,
  block/private-profile access, explicit server-managed enrollment and existing
  Connect readiness/identity gates. Trusted destination from existing records.
- Existing purchase idempotency, provider key, raw-signature webhook verification,
  payment reconciliation, refunds, disputes and transfer controls are reused.
- Retries reuse one purchase and one provider key. Failed provider responses do
  not cancel the purchase or declare it unpaid. Redirects never confirm payment.
- Receipt status remains readable by its authenticated buyer after creator
  eligibility changes; revocation and account ownership are still enforced.
- Status distinguishes confirming, confirmed, refunded, partially refunded,
  disputed and payment-received-under-review. It does not erase recovery cases.
