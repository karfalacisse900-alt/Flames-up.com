Confirmed code defects / changes
-------------------------------
1. Home and Details used different rendering policies within the same selected
   frame. Home applied CaptroPostMediaView/sourceRect; Details used fit on the
   uncropped original. PostDetailOptimizedMediaCarousel.mediaSlide now uses the
   same crop renderer as Home. Details' existing native TabView paging remains.
   Fullscreen viewing deliberately retains fitted originals. App cover writing
   remains hidden in Details. No supported-ratio policy was changed.

2. Home stored every carousel selection and stamp measurement in parent @State
   dictionaries. Swiping/measuring a single row invalidated the parent feed.
   CaptroFeedRowStateStore retains row-local ObservableObjects without publishing
   child changes to Home. Media selection remains stable through lazy remounting.
   Repeated selection writes are coalesced; media ID generation no longer hashes
   every URL again for every individual slide.
   This proves unnecessary invalidation existed, NOT that it caused all reported
   device shaking or freezes.

3. The existing social camera lacked a return/restart path, mixed capture commands
   across queues, forced portrait output, used deprecated photo sizing and could
   discard a successfully finalized duration-limited movie because an error was
   present. Capture, Post and Story cameras now use one serialized foundation:
   CaptroCameraCaptureService (AVCapturePhotoOutput + AVCaptureMovieFileOutput).
   Lifecycle, format, permission, orientation, duplicate-shutter, storage and
   recording-finalization decisions are centralized. No alternate competing
   session implementation was added to the new tab.

4. Unchanged PNG/WebP image bytes were being uploaded as image/jpeg/*.jpg.
   MIRAMediaUploadService now preserves supported original bytes/MIME for both
   Posts and Stories, detects HEIC/HEIF, and preserves dimensions/orientation in
   the oversized-image fallback. Compression and cancellation are off-main.
   Story publishing no longer assigns every video a 15-second duration; it uses
   the existing server's 15/30/60-second bucket covering the validated clip.

5. Independent review of the new camera found permission-sheet lifecycle and
   reconfiguration recovery races. Permission completion now reconciles current
   active mode rather than discarding a grant after a scene-generation change.
   Failed reconfiguration invalidates configuration before retry. Offscreen flip
   and missing audio input have explicit guards/feedback. These are code-path
   findings with injected-boundary tests, not reproduced hardware failures.

6. Every mounted Home carousel could replace the same global video-preload
   desired set as MainFeedModel, cancelling/evicting other rows' prepared work.
   Home now has one existing owner (MainFeedModel); selected stable media and
   adjacent slides get priority. Background revalidation does not reset that
   neighborhood to the first post. Row-local image prefetch remains bounded.
   This confirms competing requests, not a measured cause of the user's freeze.

7. Restoring a 10-item draft then handing off a camera capture could append an
   11th item. The existing draft stays untouched, the capture remains pending,
   and an explicit Add capture retry becomes available after making room.
   Publishing is blocked while that capture is unresolved. Regression tests
   cover retention, retry, bounds and restored-capture deduplication.

Capture screen flow
-------------------
Existing Capture tab -> Photo/Video camera -> Retake / Use photo or video ->
existing Post or Story composer -> deliberate publishing through existing flow.
The captured original remains available when the composer is cancelled. Camera
state is account-scoped. No library importing or Photos permission is added to
Capture. Existing composer gallery/editing tools remain available.

Photo mode uses full photo output, active-format supported max dimensions and
quality prioritization; HEIF where available, JPEG fallback. Review provides one
reversible Enhance treatment with original/enhanced comparison. Enhancement is
on-device, explicit, and retains the original; no upscaling or cloud processing.

Video mode is intentionally 1080p/30 SDR H.264 with supported stabilization,
60-second / 200MB existing limits. The current Cloudflare Stream delivery path
tops out at 1080p, so the UI does not promise end-to-end 4K or unverified HDR/HEVC.
Zoom is the actual wide-camera factor; no false ultrawide/telephoto lens labels.
Changing recording camera/lens is disabled rather than implying seamless switching.
