# Captro marketplace payment rebuild — 26 September 2026

## Deployed scope and root causes

Active target: native SwiftUI Captro (com.captro.app), Stripe iOS 26.9.0. Branch: feature/recorded-voice-moderation. Application/backend release source: 1332ae74. Existing Cloudflare Worker and Supabase project are retained; no replacement backend, SDK or database.

The old buyer handler and PaymentIntent adapter required a payout-ready seller. The success handler also tried to transfer seller funds before issuing access. This was incompatible with the requested platform-first marketplace model. The saved-card error was generated by the seller preflight catch; it did not prove that a card had been attempted or declined.

A second defect caused RPC error extraction to report the function name CAPTRO_BEGIN_MARKETPLACE_PURCHASE_V2 instead of the actual CAPTRO_CAPACITY_REACHED exception. Real sandbox tests exposed this and it is fixed. The new ledger's first implementation also exposed a BEFORE INSERT/upsert side-effect bug; it was corrected to AFTER mutation triggers and regression-tested before deployment.

The historical access-refresh screenshot came from PostDetailNativeView.loadCommerce, GET /commerce/posts/:postId. Its original underlying exception was not retained, so its precise historical cause is not established. The deployed route now passed authenticated reads for both current paid records; cached details remain visible on refresh failure.

## Buyer and money path

- Existing /payments/create and alias /checkout/create-payment-intent validate the authenticated buyer, object/tier, quantity, authoritative price, currency and atomic inventory hold.
- PaymentIntent is on the platform: no destination charge and no immediate seller transfer. Stored Stripe Customer resources are checked in the current environment; a missing customer is replaced. Optional CustomerSession failure does not prevent new-card checkout. No saved PaymentMethod is required.
- Official native PaymentSheet handles card entry/authentication. Its completion is not payment authority. Signed webhooks and server Stripe retrieval verify intent identity, amount, currency and successful payment before issuing access.
- Existing app_purchases is the order table: confirmed means paid/confirmed access. Stable IDs, operation keys, snapshot prices and existing refund/dispute states are reused rather than duplicating order tables.
- Successful payment atomically issues the existing entitlement/ticket and pending earnings. The receipt displays price, quantity, tax, fee, total, date and safe card brand/last-four when available.
- Existing versioned, HMAC-authenticated random-UUID QR tokens remain compatible. They contain no card details, client secret or identity details. Host validation is read-only; Check In/ Redeem revalidates under server locks. Duplicate, refunded, invalid and wrong-host scans are rejected.
- Joined counts now reflect confirmed access, not temporary payment holds. Inventory still reserves pending checkout places.

## Earnings, release and payout

app_marketplace_ledger is append-only and inaccessible directly to app clients. Balances are derived by seller, currency and Stripe mode. app_creator_earnings is the operational projection, not stored money. Pending, Clearing, Available, transfer, payout, refund and dispute movements append ledger entries. Duplicate upserts do not multiply balances.

A release requires completed service, explicit audited review with a release time, actual known Stripe processing cost, cleared Stripe funds, no refund/dispute/reconciliation hold, and a current eligible seller account. Future Event/Meetup end times cannot be bypassed by a buyer acknowledgement. Seller onboarding does not block the original buyer purchase.

POST /commerce/purchases/:id/complete accepts only that order's buyer; it does not release money. Authorized financial operators review via POST /admin/commerce/purchases/:id/release with note and releaseAfter (ISO timestamp). The approval is recorded atomically in the immutable ledger. There is no fabricated universal clearing period: Captro operations must apply its approved release/refund policy. Unreviewed earnings remain pending. Due approved releases are reconciled by the existing scheduled worker.

Transfers use a durable lease, immutable amount/destination snapshot, source charge, transfer-group lookup and stable Stripe idempotency key. Ambiguous attempts older than the safe idempotency window require review instead of risking another transfer. Refund/dispute races reverse or hold funds; insufficient recovery remains a reconciliation issue, never fake recovery. Partial-refund or dispute-reversal re-release requires operator review.

Withdrawals use the existing current Connect eligibility, actual Stripe balance, supported debit destination, quoted fee policy and idempotent payout request. A transfer is not a payout. Captro currently absorbs the configured instant-payout fee; this work does not invent a new fee business rule. Separate Stripe Identity remains optional/configured in addition to Connect KYC; its native document capture was not exercised here.

Both sandbox and live PLATFORM payout schedules were changed from daily to manual, as required to retain funds in Stripe for later transfers. Existing SELLER schedules were not changed; a non-manual seller cannot receive a new deferred release until reviewed. This is not escrow. Operators must monitor unfulfilled/unclaimed balances, disputes and applicable Stripe holding limits; manual does not mean indefinite holding. See [Stripe separate charges and transfers](https://docs.stripe.com/connect/separate-charges-and-transfers) and [manual payout guidance](https://docs.stripe.com/connect/manual-payouts).

## Not claimed

No real-money charge or payout was performed. Native PaymentSheet, Apple Pay, bank/3DS interaction and QR camera scanning have not been physically tested on an iPhone. The sandbox proves backend money/access behavior, not native device behavior or legal approval. No separate Stripe Identity SDK capture, country-by-country payout eligibility or full dispute lifecycle was device-tested. Live sellers with outstanding Stripe requirements must complete those before transfer/payout, not before buyers pay.

TestFlight release availability is recorded separately after Apple's processing completes; a successful upload alone is not tester availability.
